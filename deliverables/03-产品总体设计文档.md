# 产品总体设计文档

## 1. 项目背景

智游景行面向景区数字化导览场景，解决传统人工导游资源有限、固定录音讲解缺少互动、游客个性化需求难满足、景区运营反馈滞后的问题。系统以 AI 数字人为核心交互入口，结合景区知识库、知识图谱、语音识别、语音合成和运营分析，形成游客服务与管理决策闭环。

## 2. 设计目标

1. 为游客提供文本、语音、数字人讲解等多模态导览体验。
2. 基于景区知识库回答历史、文化、路线、服务设施等问题。
3. 根据游客偏好、游览时长和场景条件生成个性化路线。
4. 汇总游客对话和评价，辅助景区管理方发现服务问题。
5. 支持后台维护知识库、数字人形象和运营数据。

## 3. 总体架构

```text
游客浏览器 / 移动端
  |
  | HTTP / WebSocket
  v
frontend-web (Vue3 + Vite)
  |-- 游客端：路线推荐、AI 问答、数字人讲解
  |-- 管理后台：知识库、数字人、服务建议
  |-- 数据大屏：问答热度、满意度、景点热力
  |
  | /api /static
  v
Orchestrator (FastAPI)
  |-- chat：文本/语音对话编排
  |-- route：知识图谱路线规划
  |-- admin：后台管理接口
  |-- analytics：运营统计接口
  |
  | 外部与基础服务
  v
Dify / LLM / RAG
FunASR
CosyVoice2 或其他 TTS
PostgreSQL
Redis
Neo4j
```

## 4. 技术选型

| 模块 | 技术 | 说明 |
|---|---|---|
| Web 前端 | Vue3、Vite、Pinia、Vue Router | 统一 Web 入口，支持游客端、后台、大屏 |
| 数字人渲染 | three.js、three-vrm、VRM | 浏览器本地渲染数字人，降低服务端 GPU 依赖 |
| 口型同步 | Web Audio API、频谱分析 | 前端根据音频驱动口型变化 |
| 后端服务 | FastAPI、Pydantic、SQLAlchemy | API 编排、数据校验与业务服务 |
| 知识问答 | Dify、RAG、LLM | 基于景区知识库生成回答 |
| 语音识别 | FunASR | 游客语音转文本 |
| 语音合成 | CosyVoice2 / Edge / Doubao / Fish TTS | 多 TTS 适配和降级 |
| 数据库 | PostgreSQL | 会话、消息、形象、建议等业务数据 |
| 缓存 | Redis | 会话与临时状态 |
| 知识图谱 | Neo4j | 景点关系与路线规划 |
| 部署 | Docker Compose、Nginx | 容器化运行和静态资源托管 |

## 5. 核心功能设计

### 5.1 AI 数字人导览

游客在 Web 端输入文字或语音问题，前端调用 Orchestrator。后端完成语音识别、知识问答、TTS 合成和动作标签生成，前端播放语音并驱动 VRM 数字人的口型、表情和动作。

关键路径：

```text
游客提问 -> frontend-web -> /api/chat -> Dify/RAG -> TTS -> 数字人播报
```

### 5.2 景区知识问答

系统通过 Dify 和本地知识库提供景区历史、文化、景点、设施、游览建议等问答能力。后端保留本地兜底逻辑，避免外部服务不可用时系统完全失效。

### 5.3 个性化路线规划

游客选择偏好和游览时长后，后端读取知识图谱中的景点主题、步行关系和建议停留时间，按游客兴趣计算得分，并生成推荐路线和讲解开场白。

路线规划考虑：

| 因素 | 说明 |
|---|---|
| 游客兴趣 | 历史、自然、建筑、亲子、拍照等 |
| 时间约束 | 根据游览时长控制路线长度 |
| 景点关系 | 使用 Neo4j 或 JSON 兜底数据 |
| 讲解内容 | 结合 LLM 生成自然语言说明 |

### 5.4 运营后台

后台用于维护数字人形象、动作、知识库文件和服务建议。管理员可上传 VRM 模型和知识文档，查看游客反馈聚合结果。

### 5.5 数据大屏

数据大屏展示系统运营状态，包括服务人次、热门问题、满意度趋势、景点热度和服务建议，为景区管理提供实时参考。

## 6. 数据设计

主要数据表：

| 表 | 说明 |
|---|---|
| `conversation` | 会话、游客画像、数字人配置 |
| `message` | 用户与数字人的消息、意图、情感、引用来源 |
| `avatar` | 数字人形象、声音、默认配置 |
| `suggestion` | 服务建议、优先级、证据、处理状态 |

知识图谱模型：

```text
(Park)-[:HAS_SPOT]->(Spot)-[:NEXT_TO]->(Spot)
```

其中 `Spot` 保存景点名称、主题标签、推荐停留时间和亮点说明。

## 7. 接口设计

| 方法 | 路径 | 说明 |
|---|---|---|
| `POST` | `/api/chat/text` | 文本问答 |
| `POST` | `/api/chat/voice` | 语音问答 |
| `POST` | `/api/chat/interrupt` | 打断数字人播报 |
| `GET` | `/api/chat/avatar-stream` | 获取数字人资源 |

| `GET` | `/api/analytics/overview` | 大屏概览 |
| `GET` | `/api/analytics/hot-questions` | 热门问题 |
| `GET` | `/api/analytics/suggestions` | 服务建议 |
| `POST` | `/api/admin/login` | 管理员登录 |
| `GET/POST/DELETE` | `/api/admin/avatars` | 数字人管理 |
| `POST` | `/api/admin/knowledge/upload` | 知识库上传 |

完整接口以 FastAPI 自动生成文档为准：

```text
http://localhost:8010/docs
```

## 8. 安全设计

1. 管理后台写操作使用 JWT 认证。
2. API Key、数据库密码等敏感配置只写入 `.env`，不写入代码。
3. LLM 输出仅作为文本或 JSON 使用，不直接执行。
4. Pydantic 对请求和响应进行结构校验。
5. Nginx 统一代理 `/api` 和 `/static`，避免前端硬编码生产后端地址。

## 9. 自研与复用边界

| 类型 | 内容 |
|---|---|
| 自研 | Orchestrator 编排层、路线规划、情感分析、服务建议、Web 交互、后台、大屏、数字人集成 |
| 复用 | Dify、LLM、FunASR、TTS 引擎、three-vrm、PostgreSQL、Redis、Neo4j |

系统设计原则是复用成熟 AI 与基础设施能力，把自研重点放在景区业务闭环、数字人体验和运营分析上。
